## 2. 根因：本地代理 127.0.0.1:7897 的 TLS 握手超时

诊断结果：

| 路径 | 结果 |
|---|---|
| `curl --noproxy '*' https://api.deepseek.com` | **HTTP 401（说明直连可达）** |
| `curl -x http://127.0.0.1:7897 https://api.deepseek.com` | **Connection timed out** |
| Python `urllib.request.getproxies()` | `http/https/ftp = http://127.0.0.1:7897` |
| Python `urlopen(... api.deepseek.com ..., timeout=15)` 使用默认代理 | **TLS handshake timed out** |
| Python `urlopen(... timeout=15)` 设置 `NO_PROXY=api.deepseek.com` | **HTTP 401，0.3 秒内返回** |
| 代理进程 | `verge-mihomo`（PID 16588，监听 127.0.0.1:7897） |
| 系统设置 | IE/系统代理 `127.0.0.1:7897` 已启用；WinHTTP 显示直连 |

也就是说：**网本身能到 DeepSeek，但当前代理节点/订阅对 `api.deepseek.com` 的 TLS 握手卡死**。

`core/chat.py` 的 `urlopen(timeout=300)` 对每个请求最多等 300 秒。`kp_build` 的并发 worker 会同时撞上这个超时，逐个失败，批任务看起来长时间不动。`RemoteUnknown` 逻辑做得对：不自动重发；但“每条都等满 300 秒”让用户感知为卡死。这不是 `kp_build` 死锁。
